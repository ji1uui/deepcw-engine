# DeepCW GUI アプリケーション 要件定義書

**対象**: `lazarus/` の Free Pascal / Lazarus デスクトップアプリケーション
**版**: 2.4（2026-09-02）／ 設定画面を整理し、実装間の不整合と潜在不具合を除去
**状態**: ドラフト

---

## 1. この文書について

### 1.1 改訂の要点

版 1.0 は、リファレンス実装（web-deep-cw-decoder）の設計を要件へ写し取った部分が多かった。
版 2.0 では**「アプリを使う人がどう感じるか」を先に置き、そこから逆算して制約を精査した**。
その結果、次の 3 点が変わっている。

| # | 変更 | 理由 |
| --- | --- | --- |
| 1 | **第 3 章「制約の精査」を新設し、本書の中心に据えた** | 制約には、利用者に見せてよいものと、アプリが飲み込むべきものがある。1.0 はこれを区別せず、engine の都合をそのまま要件にしていた |
| 2 | **和文 CW を将来対応とし、初版のスコープから外した** | 依頼による。あわせて、和文のために必須としていたメタデータ拡張を「前提条件」から「将来の拡張点」へ降格した |
| 3 | **送信機能を本書から分離した** | 依頼により、実際に電波を出す送信は Hamlib を前提とした別仕様で整理する。本書には**練習用の信号生成**だけが残る（境界は第 7 章） |

### 1.2 スコープ

| 含む | 含まない |
| --- | --- |
| 受信・同調・確認・記録・練習・診断の体験 | **電波を出す送信**（Hamlib 前提の別仕様） |
| エンジンの組み込み方式と配布形態 | **和文 CW**（将来対応。第 7 章に受け口のみ記す） |
| 利用者に見せる情報と見せない情報の切り分け | ニューラルネットワークの学習・再学習 |

## 2. 体験の目標

### 2.1 誰が、どんな状況で使うのか

| # | 場面 | 利用者が得たいもの | 本書での重心 |
| --- | --- | --- | --- |
| **A** | 常設シャックで 7MHz を流し聞きし、気になった局を拾う | **聞きながら読む補助**。全文を機械に任せたいのではない | FR-B, FR-C, FR-D |
| **B** | 縦振り・バグキーで自分の符号を確認する | **自分の癖が見えること** | FR-F |
| **C** | 録音した QSO を後から読み直す | **落ち着いて確認できること** | FR-E |

いずれの場面でも、本レポートが示す国内の共通認識——**デコーダは人間の耳と脳の置き換えではなく、
補助と練習の道具である**——を前提に置く。

### 2.2 体験として満たすべき 5 つのこと

1. **入れてすぐ動く。** 追加の導入作業を求めない。
2. **待たされない。** 符号を聞いてから文字が出るまでが会話の速さに追いつく。
3. **嘘をつかない。** 確からしくない文字を、確かな文字と同じ顔で出さない。
4. **落ち着いて読める。** 一度出た文字が勝手に書き換わらない。
5. **困ったときに次の一手がわかる。** エラーが症状ではなく対処を伝える。

## 3. 制約の精査

本書の中心。制約を 3 つに分ける。**A は利用者に見せてはならない。B は引き継がない。C だけが残る。**

### 3.1 A — 利用者に見せてはならない制約

エンジンの都合であって、利用者の関心事ではないもの。**アプリが内部で飲み込む。**

| 制約 | 現状の露出 | あるべき体験 | 要件 |
| --- | --- | --- | --- |
| 入力長 5–20 秒 | 「5〜20 秒でなければなりません」とエラー表示 | **利用者はこの制限を知る必要がない。** 常時受信では起動直後だけ「受信中…」と出す。ファイルは短ければ無音で補い、長ければ黙って分割する | FR-B.1 |
| 窓分割と重なり | 内部だが、継ぎ目の誤りが文章に出る | 継ぎ目の存在を知覚させない | FR-B.4 |
| 復調帯域 400–1200 Hz | 内部 | 帯域外をクリックしたら「範囲外」ではなく、**読める音程へ寄せる案内**を出す | FR-D.4 |
| サンプリング周波数 3,200 Hz / FFT 256 / ホップ 48 | 設定タブに常時表示 | 診断画面へ移す。運用中は見えなくてよい | FR-G.3 |
| 推論スレッド数 | 設定タブの主要項目 | **自動決定する。** アマチュア無線家にスレッド数を決めさせない | FR-G.2 |
| ONNX Runtime / PortAudio の所在 | 設定タブの主要項目。未導入なら受信できない | **同梱して既定で不要にする**（3.3 参照）。見つからないときだけ導線を出す | FR-A.1 |
| モデル・メタデータのパス | 設定タブの主要項目 | 既定で自動。差し替えは詳細設定 | FR-G.3 |

#### エラー文言の実態

現行実装が利用者に出しうる文言を調べたところ、**そのほとんどが開発者向けだった。**

| 現状の文言 | 利用者にとっての問題 | あるべき文言の性質 |
| --- | --- | --- |
| `Reflect padding by 128 needs at least 129 samples, got 40.` | 何を指しているか分からない | そもそも表に出さない（内部で処理） |
| `The audio must last between 5 and 20 seconds…` | エンジンの都合を押しつけている | 表に出さない（FR-B.1） |
| `Could not open the output stream: Invalid device` | 原因は分かるが対処が分からない | 「再生装置を開けませんでした。別の装置を選ぶか、他のアプリが使用中でないか確認してください」 |
| `Metadata expects 65 frequency bins, but the geometry yields 64.` | 利用者には手の打ちようがない | 「モデルファイルと設定ファイルの組み合わせが正しくありません」＋差し替え導線 |
| `Pa_Initialize failed: …` | ライブラリ名は利用者の語彙にない | 「音声装置を初期化できませんでした」＋診断画面への導線 |

**要件**: 利用者に届く文言は、**何が起きたかと、次に何をすればよいかを日本語で述べる**。
ライブラリ名・関数名・テンソル形状を含む文言は診断画面にのみ出す（FR-A.4, NFR-5.4）。

### 3.2 B — 参照実装から引き継がない決定

web 版の設計は**ブラウザという環境への最適解**であり、デスクトップアプリの最適解とは限らない。

| 参照実装の決定 | 引き継がない理由 | 代わりにどうするか |
| --- | --- | --- |
| Normal / Pileup / Benchmark の**モード切替** | モード切替は「いま自分はどのモードか」を利用者に覚えさせる。常設機では画面は 1 つでよい | 単一の受信画面。検出した信号はそのまま提示する |
| **WASM / WebGPU のエンジン選択** | ブラウザ固有の事情。デスクトップに持ち込む意味がない | 自動。診断画面に結果だけ表示 |
| **ベンチマークを運用機能として提供** | 性能計測は診断であって運用ではない | 診断画面の 1 機能へ（FR-G.4） |
| **復調窓 6/12/18/30 秒の選択** | 利用者は「窓」という概念を持たない | 「速さ優先／確実さ優先」の 2 択にし、窓は内部で決める（FR-B.3） |
| **30 秒まで伸ばしてから確定**という時間設計 | ブラウザの CPU 制約に由来する。デスクトップには**実測 40–60 倍の余裕がある** | **より短い間隔で推論し、遅延を削る**（NFR-1） |
| **PWA・オフラインキャッシュ** | デスクトップアプリには不要 | — |
| 帯域幅 5 段階の**手動選択** | 初期状態で選択を迫るのは負担 | 既定は自動。手動は残すが詳細扱い（FR-D.3） |
| **語のクリックで再デコードするポップアップ** | — | **引き継ぐ。** 「怪しい語をその場で確かめる」は本レポートの懸念に直接答える最良の体験（FR-C.3） |
| **確定テキストと暫定テキストの分離** | — | **引き継ぐ。** 体験目標 4 そのもの（FR-B.2） |
| **周波数シフト方式の同調** | — | **引き継ぐ。** ただし利用者に見えるのは「クリックした信号が読める」ことだけ（FR-D.1） |

### 3.3 C — 本当に残る制約

| 制約 | 内容 | 影響と対処 |
| --- | --- | --- |
| **外部ライブラリの導入** | 受信には ONNX Runtime、音声入出力には PortAudio が要る | **調査の結果、ONNX Runtime は MIT、PortAudio も MIT 系であり、AGPL のアプリに同梱して配布できる。** 初版から同梱し、「自分で入れてください」を初回体験から消す（FR-A.1） |
| **AGPL-3.0-only** | 改変・サービス提供時にソース提供義務 | ログソフト等との連携は**プロセス間の疎結合**に限る（FR-E.4） |
| **無線機から PC への音の経路** | 利用者の設備に依存し、アプリでは解決できない | 解決はできないが**支えることはできる**。装置一覧・レベル表示・「音が来ているか」の明示（FR-A.2, FR-A.3） |
| **モデルの精度は所与** | 学習済みモデルを改善する手段がない | 我々の責任は**前処理を誤らないこと**に限られる。参照実装との一致を自動検証し続ける（NFR-2） |
| **文字集合は英文のみ** | A–Z、0–9、`,` `.` `/` `?`、空白 | 和文は将来対応（第 7 章）。**送信できない文字を送信欄で受け付けない**など、境界を明示する |
| **実時間性は機器依存** | 古いシャック PC でも使われる | 自己計測し、遅延目標を満たせない場合は**自動的に間隔を緩める**（FR-G.4, NFR-1.4） |

### 3.4 実測にもとづく 2 つの前提

版 1.0 で確認した事実は、体験の観点から見ても要件の土台になる。

| 実測 | 体験上の意味 |
| --- | --- |
| モデル出力は **log-softmax**（1 フレームの `exp` 総和 = 1.000） | **確信度は推論を 1 回も増やさずに得られる。**「嘘をつかない」（体験目標 3）が無償で手に入る |
| 入出力の時間次元が **1 : 1**（15 ms 分解能） | 文字がいつ鳴ったかが分かる。**語のクリック再デコード・ウォーターフォールとの整列・フィスト計測**がすべて成立する |
| 実時間比 **40–60 倍**（1 スレッド・CPU） | 遅延を削る余地がある。参照実装の時間設計をそのまま踏襲する理由はない |

## 4. 機能要件

優先度は **必須**（初版に不可欠）／**推奨**（初版で強く望まれる）／**任意**（将来版で可）。

### FR-A 立ち上がりの体験

> **目標**: 導入した人が、説明書を読まずに受信を始められる。

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-A.1 | ONNX Runtime・PortAudio・モデル・メタデータを**同梱して配布する**。利用者による事前導入を求めない | 必須 | 素の OS に展開して起動し、追加作業なしで受信できる |
| FR-A.2 | 起動直後の画面から、**操作 1 回で受信を開始できる** | 必須 | 起動から受信開始までの操作が 1 回、5 秒以内 |
| FR-A.3 | 入力装置を一覧から選べ、**音が届いているかを常時表示する**（レベル表示と無音の明示） | 必須 | 音の有無を 1 秒以内に判別できる |
| FR-A.4 | 起動できない・受信できない場合、**症状ではなく対処**を日本語で提示し、診断画面へ導く | 必須 | **実装済**。原文は診断情報に記録し、設定タブに表示する |
| FR-A.5 | 前回の設定と装置選択を復元する | 必須 | **実装済**（装置選択の復元は未） |

### FR-B 受信の体験

> **目標**: 聞いている符号に、文字が遅れずについてくる。一度出た文字は動かない。

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-B.1 | エンジンの入力長制限（5–20 秒）を**利用者に露出しない**。ファイルは自動で補完・分割する | 必須 | **実装済**（下限未満は無音で補完）。起動直後の「受信中…」表示は未 |
| FR-B.2 | 受信テキストを**確定部分と暫定部分に分けて表示**する。**確定した文字は決して書き換わらない** | 必須 | **実装済**（`src/deepcw.stream.pas`）。70 秒の QSO・投入の刻み 3 通りで書き換え 0 件 |
| FR-B.3 | 「速さ優先／標準／確実さ優先」を選べる。末尾ガードと最小確定長は内部で決める | 推奨 | **実装済**（受信タブ「文字が決まるまで」） |
| FR-B.4 | 窓の継ぎ目に起因する誤字・重複・欠落を生じない | 必須 | **実装済**。流し込みでも一括復号と 1 文字も違わない |
| FR-B.5 | 受信テキストを遡って読め、**検索できる**。自動追尾は上へスクロールすると止まる | 推奨 | 遡りと追尾停止は**実装済**。検索は未 |
| FR-B.6 | 受信テキストを時刻付きでファイルへ追記保存する。異常終了しても直前まで残る | 推奨 | 強制終了後に直前 1 行まで残存 |

### FR-C 信頼の体験

> **目標**: 機械が自信のない文字を、自信のある文字と同じ顔で見せない。

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-C.1 | 文字ごとの確信度を、出力フレーム群の事後確率から算出する | 必須 | 算出定義を文書化し、実装と一致させる |
| FR-C.2 | 確信度を**濃淡で表示**する。低確信度は明確に薄い | 必須 | 雑音のみの入力で出る文字がすべて低確信度側に入る |
| FR-C.3 | **語をクリックすると、その区間だけ再推論して候補を提示する** | 推奨 | 操作から提示まで 1 秒以内 |
| FR-C.4 | 表示強度を調整、または無効化できる | 推奨 | 設定が永続化される |
| FR-C.5 | 確信度を「正しさ」と断定する語で説明しない | 必須 | UI 文言のレビューを通す |

### FR-D 同調の体験

> **目標**: 読みたい信号をクリックすれば、それが読める。

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-D.1 | ウォーターフォールのクリックで復調対象を移す | 必須 | クリック位置との誤差 1 ビン（12.5 Hz）以内 |
| FR-D.2 | ホイール／上下キーで微調整できる | 必須 | 1 操作 ≦ 12.5 Hz |
| FR-D.3 | 帯域幅は既定で自動。手動選択は詳細設定に置く | 推奨 | 自動のまま実用に足る |
| FR-D.4 | 復調可能な帯域の外を選んだとき、**拒否ではなく案内**を返す | 推奨 | 「この音程は読めません。受信機の音程を 400〜1200 Hz に寄せてください」等 |
| FR-D.5 | 現在の復調対象をウォーターフォール上に重畳表示する | 必須 | 表示と処理対象が一致 |
| FR-D.6 | 復号文字をウォーターフォール上の対応時刻に整列表示する | 推奨 | 位置誤差 100 ms 以内 |

### FR-E 記録の体験

> **目標**: 拾ったコールサインが、手入力なしでログに届く。

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-E.1 | 受信テキスト中のコールサインを検出して強調する | 必須 | JA–JS、7J–7N、8J–8N を含む国内プレフィックスを認識 |
| FR-E.2 | コールサイン・RST を**操作 1 回でクリップボードへ**送る | 必須 | 全文コピーは**実装済**。コールサイン単位は未 |
| FR-E.3 | 交信内容を **ADIF 形式**で出力する | 必須 | ハムログ・CTESTWIN が読み込める |
| FR-E.4 | ログソフトへの直接連携は**プロセス間の疎結合**で行う（3.3 の AGPL 制約） | 必須 | 同一バイナリへの静的リンクを行わない |
| FR-E.5 | ターボハムログの入力画面へ直接転送する | 推奨 | **要調査**（第 8 章 2） |
| FR-E.6 | POTA 公園コード `JP-####`・SOTA 参照番号を検出して強調する | 推奨 | 誤検出率が実用範囲 |
| FR-E.7 | JCC/JCG コードを手入力でき、ADIF 出力に含める | 推奨 | — |
| FR-E.8 | 受信音声を WAV 録音し、後から読み直せる | 推奨 | 録音とデコードを同時に行える |
| FR-E.9 | 録音済み WAV を読み込んでデコードできる | 必須 | 既実装 |

> **第三者データを同梱しない。** JCC/JCG や QTH のデータベースは再配布可否が不明であるため、
> 利用者が用意したファイルを読む方式に限る。参照に失敗しても受信機能に影響を与えない。

### FR-F 受信練習の体験

> **目標**: 練習と実運用が同じアプリで続く。

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-F.1 | テキストから練習用 CW 音声を生成し、再生・WAV 保存できる（PARIS / ファンズワース） | 必須 | 既実装 |
| FR-F.2 | 生成音声をそのままデコーダへ通し、往復一致を確認できる | 必須 | 既実装 |
| FR-F.3 | ランダム欧文・コールサイン・QSO 定型文の受信練習を行える | 推奨 | 速度・文字集合・雑音量を設定できる |
| FR-F.4 | **遅延表示**（先に自分で写し、後から正解を出す）を選べる | 推奨 | 遅延時間を設定できる |
| FR-F.5 | 受信練習の正答率と、間違えた文字の傾向を記録する | 任意 | FR-H.9 の記録と同じ場所に残る |

### FR-H 送信訓練（フィスト・トレーナー）

> **目標**: 自分の符号を点数と履歴で見られ、どこを直せばよいかが分かる。

#### 前提：電波を出さずに成立する

無線機は鍵操作に対してモニタートーンを鳴らす。**その音を受信と同じ入力から取り込めば、
送信訓練は受信経路だけで完結する。** 送信も Hamlib も要らない（ダミーロード運用でも、
モニターのみでも同じ）。この事実により、送信訓練は本書の範囲に確定する（第 7 章 1 の解決）。

#### 測定と採点

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-H.1 | 無線機のモニタートーンを受信と同じ入力から取り込み、訓練を開始できる | 必須 | 送信を伴わずに動作する |
| FR-H.2 | **課題文モード** — アプリが課題文を提示し、操作者が送出し、終了で採点する | 必須 | 課題文は速度・長さ・内容（欧文／コールサイン／QSO 定型文）を選べる |
| FR-H.3 | **自由送出モード** — 課題文なしで送り、デコーダの結果を参照として採点する。**測定が参照に依存することを明示する** | 推奨 | 画面上で「参考値」と分かる |
| FR-H.4 | 要素タイミングは**専用の包絡線検波**（分解能 1 ms 以下）で測る。モデルの STFT（15 ms）を用いない | 必須 | 付録 A の精度を満たす |
| FR-H.5 | 短点・長点・符号内間隔・文字間間隔・語間間隔を種別ごとに分けて測る | 必須 | 課題文モードで送出値との誤差 10% 以内（付録 A） |
| FR-H.6 | 次の 5 項目を 0–100 で採点し、実効 WPM を併記する | 必須 | 付録 A の順位と再現性を満たす |
| FR-H.7 | 採点基準を **標準 / ファンズワース / バグキー / 自分の過去** から選べる | 必須 | 基準により点数が変わることを実測で示す |
| FR-H.8 | 点数だけでなく、**何を直せばよいか**を 1 文で示す | 必須 | 最も低い項目に対応した助言が出る |
| FR-H.9 | 短点・長点・各間隔の分布をヒストグラムで示す | 推奨 | 分布の重なりが目視で分かる |
| FR-H.10 | 訓練 1 回ごとの結果を記録し、**項目別の推移**を折れ線で示す | 必須 | 鍵の種類ごとに分けて表示できる |
| FR-H.11 | 自己ベスト・連続日数など、続ける動機になる情報を示す | 推奨 | — |
| FR-H.12 | 記録を CSV で書き出せる | 推奨 | 表計算ソフトで開ける |

#### 評価項目

| 項目 | 測るもの | 低いときに起きること |
| --- | --- | --- |
| **速度の安定** | 短点長のばらつき（変動係数）とセッション内のドリフト | 相手が速度を掴めない |
| **短長の明瞭** | 短点と長点の分布の分離度、および長短比 | 短点と長点が聞き分けられない |
| **区切りの明瞭** | 符号内間隔と文字間間隔の分布の**分離度** | **文字の切れ目が分からない。最も写しにくくなる** |
| **間隔の正確** | 符号内 1・文字間 3・語間 7 に対する各比の誤差 | 語の切れ目が曖昧になる |
| **写しやすさ** | 課題文に対するデコーダの文字誤り率 | 総合的な結果 |

実効 WPM は点数ではなく**文脈値**として併記する。速いことは上手いことではない。

#### 記録する項目（FR-H.10）

| 項目 | 例 |
| --- | --- |
| 日時 / 所要時間 | 2026-09-02 21:14 / 48 秒 |
| 鍵の種類 | 縦振り / パドル / バグ / エレキー |
| 課題文と文字数 | `CQ CQ DE JA1ABC K` / 17 |
| 実効 WPM | 19.7 |
| 項目別点数と総合 | 100 / 100 / 100 / 95 / 100 → 99 |
| 素の測定値 | 短点 CV、長短比、各間隔比、分離度 |
| 採点基準 | 標準 |

**素の測定値も残す。**基準や重みを後から見直したとき、過去の記録を採点し直せる。

#### 設計原則：個性を減点しない

本レポートは、バグキーの「芸術的な符号」が機械のタイミング基準で読めないことを中核的欠陥として挙げる。
**その符号を低い点数で咎める道具を作れば、同じ過ちを別の形で繰り返すことになる。**

- 点数は「正しさ」ではなく**安定と明瞭**を測る。長短比 2.6 のバグキーは、その値を基準に選べば高得点になる
- **自分の過去**を基準に選べる。「規範に合っているか」ではなく「先月より安定したか」を問える
- 点数の低さは**故障ではなく余地**として提示する。「直すとよい点」であって「誤り」ではない

> **付録 A の実測**: 12% のばらつき・長短比 2.6・25% の速度ドリフトを、DeepCW はいずれも
> 文字誤り率 0% で読んだ。**機械が読めない符号と、点数が低い符号は同じではない。**
> 点数は「いま読めるか」ではなく「混信や落ち込みが加わっても読めるか」の余裕を測っている。

## 7. 他仕様との境界

### 7.1 送信（Hamlib 前提・別仕様）

本書は**電波を出す送信を扱わない**。別仕様で整理する。両者の境界を次のとおり定める。

| 本書の範囲 | 送信仕様の範囲 |
| --- | --- |
| 練習用の音声生成（FR-F.1–F.2） | 無線機の鍵操作（Hamlib 経由の CW 送出、PTT 制御） |
| 生成音声の自己デコード | 送信中の受信ミュート／サイドトーン監視 |
| 符号表と PARIS / ファンズワースの時間計算 | 定型文送出、エレキー、速度連動 |
| **送信訓練（FR-H）** — 無線機のモニタートーンを聞いて採点する | 実際に電波を出す運用 |

**送信訓練が本書に属する理由**: 無線機は鍵操作に対してモニタートーンを鳴らす。その音を
受信と同じ入力から取り込めば、**訓練は受信経路だけで完結し、送信も Hamlib も要らない。**
版 2.0 で未解決としていた帰属は、これで確定する。

**受信側が送信仕様へ提供すべき受け口**（本書では実装せず、設計上の穴だけ空けておく）:

1. **符号生成の共有** — 練習用に用いている符号表と時間計算を、送信側から呼べる形にしておく
2. **送信中の受信抑制** — 外部から「送信中」を通知され、受信処理を止められること
3. **周波数情報の受け取り** — Hamlib が無線機から得た周波数・モードを表示とログに反映できること

> **なお**: 送信仕様側が実装する「無線機を鳴らす」機能ができれば、**アプリが課題文を自動送出し、
> それを操作者が写す**という逆向きの練習も成立する。その際は FR-F.3 の課題生成を再利用できる。

### 7.2 和文 CW（将来対応）

初版のスコープ外とする。将来対応にあたり必要になるものを記録しておく。

| 項目 | 内容 |
| --- | --- |
| モデル | リファレンス実装は和文モデル（カタカナ 67 文字＋ブランク）を持つが、**本リポジトリには同梱されていない**。入手が前提 |
| メタデータ | 現行スキーマは `normalization: log1p` と反射パディングしか表現できない。和文モデルが CMVN 正規化・パディングなしであれば、`normalization` / `framing.pad` / `framing.center` / `input_seconds` の 4 キーを追加する必要がある |
| 設計上の備え | 文字集合・正規化・フレーミングを**メタデータ駆動のまま保つ**こと。特定の値をコードに埋め込まない |
| 体験 | 欧文と和文の切替、あるいは併記。色だけに頼らない区別（NFR-5.4） |

**第 1〜3 段階の実装で、上記の「設計上の備え」だけは守る。**それ以外は将来版で扱う。

### 7.3 Web 版との役割分担

Android・iOS で動作する。**Lazarus 版がモバイルを追うより、役割を分けるほうが合理的**と考える。

- **Lazarus 版** — シャックの常設機。長時間運用、ログ連携、練習、診断
- **Web 版** — 移動運用。持ち運び、セルフスポット

## 付録 A — 送信訓練の測定と採点の検証

FR-H を仕様に入れる前に、**そもそも測れるのか、点数が意味を持つのか**を合成信号で確かめた。
検証コードは本書と同じ考え方の試作であり、実装そのものではない。

### A.1 検証の方法

不完全さを制御できる CW を合成し（ばらつき・長短比・各間隔比・速度ドリフトを指定）、
帯域通過 → 整流 → 平滑の包絡線検波で要素長を取り出して、送出値を復元できるかを見た。
あわせて同じ音声を DeepCW デコーダに通し、文字誤り率を測った。
課題文は 68 文字の QSO 定型文、20 WPM、700 Hz。

### A.2 分かったこと

#### 1. モデルの STFT では粗すぎる（FR-H.4 の根拠）

20 WPM の短点は 60 ms。モデルの時間分解能 15 ms では 1 要素あたり最大 ±12.5% の量子化誤差になり、
**熟練者の 3% のばらつきを測ることができない。** 要素タイミングには専用の検波が要る。

#### 2. 課題文が既知なら正確に測れる。未知だと悪いフィストほど歪む（FR-H.2 / H.3 の根拠）

種別をしきい値（2 dit・5 dit）で分ける方式と、課題文から種別を決める方式を比較した。

| 送出した値 | しきい値方式の測定 | 課題文既知の測定 |
| --- | --- | --- |
| 初級・文字間 2.2 dit | **2.82**（誤り 28%） | **2.00**（送出値のばらつき内） |
| ファンズワース・文字間 6.0 dit | **測定不能**（語間と誤分類） | **5.87** |
| ファンズワース・語間 12.0 dit | 7.57（誤り 37%） | **11.77** |

**しきい値方式は、間隔が接近したり離れたりしたときに破綻する。**つまり、直したい相手であるはずの
悪いフィストほど測れない。課題文モードを主とする理由がここにある。

#### 3. 5 項目の採点は順位も再現性も満たす（FR-H.6 の根拠）

| ケース | 速度の安定 | 短長の明瞭 | 区切りの明瞭 | 間隔の正確 | 総合 | **CER** |
| --- | --- | --- | --- | --- | --- | --- |
| 熟練（ばらつき 3%） | 100 | 100 | 100 | 95 | **99** | 0.0% |
| ファンズワース（文字間 6） | 90 | 100 | 100 | 94 | **97** | 0.0% |
| バグキー風（長短比 2.6） | 81 | 89 | 90 | 93 | **90** | 0.0% |
| 速度ドリフト 25% | 59 | 64 | 67 | 92 | **75** | 0.0% |
| 中級（ばらつき 12%） | 47 | 53 | 47 | 88 | **65** | 0.0% |
| 初級（ばらつき 25%・比 2.4・文字間 2.2） | 18 | 6 | **0** | 47 | **12** | **27.9%** |

同じ技量・同じ課題文で乱数の種を変えて 5 回試したときの総合点の標準偏差は **0.7〜2.8 点**。
**5 点の改善は誤差ではなく上達である**と言える精度がある（FR-H.10 の推移表示が意味を持つ根拠）。

#### 4. 「区切りの明瞭」が写しやすさを決めている

初級ケースだけが文字誤り率 27.9% で、そのとき**区切りの明瞭が唯一 0 点**だった。
符号内間隔と文字間間隔の分布が重なると、人にも機械にも文字の切れ目が分からなくなる。
**点数がなぜ低いのかと、なぜ写してもらえないのかが、同じ 1 項目で説明できる。**

#### 5. 点数が低い符号と、読めない符号は違う

中級（総合 65）・バグキー風（90）・速度ドリフト（75）は、**いずれも文字誤り率 0%** だった。
DeepCW は 12% のばらつき、長短比 2.6、25% の速度ドリフトを一字も誤らずに読んでいる。

これは 2 つのことを意味する。

- **本レポートがバグキーについて指摘する問題に対し、本エンジンは実際に強い。**
  タイミング比を仮定しない設計の利点が、数値として確認できた
- **点数は「いま読めるか」ではなく「余裕があるか」を測っている。**
  総合 65 の符号は静かな条件では読めるが、混信と落ち込みが加われば先に崩れる。
  点数の意味をこのように説明すれば、低い点数が人を責めるものにならない

### A.3 この検証の限界

- **合成信号での検証にとどまる。**実際の鍵で送出された符号、実際の無線機のモニタートーン、
  実際の音声経路での検証は行っていない（未解決事項 7）
- 採点の重みは暫定値である。実際の操作者が試して初めて妥当性が判断できる（未解決事項 1）
- 課題文モードの種別対応づけは、**要素の数が一致すること**を前提にしている。
  符号が抜けた・くっついた場合の扱いは実装時に定める必要がある

## 付録 B — 確信度の定義（未解決事項 3 の決着）

### B.1 集約方法の選定

CTC の貪欲経路では、1 文字が複数フレームにまたがって出力される。その区間の事後確率を
どう 1 つにまとめるかを、**正しい文字と誤った文字をどれだけ分離できるか**で選んだ。

合成信号（22 WPM、雑音を 6 段階、各 4 種）で 1,532 の正しい文字と 28 の誤った文字を集め、
AUC（正しい文字の確信度が誤った文字より高くなる確率）で比較した。

| 集約方法 | AUC | 正の中央値 | 誤の中央値 |
| --- | --- | --- | --- |
| **最小値** | **0.897** | 1.000 | 0.988 |
| 幾何平均 | 0.896 | 1.000 | 0.994 |
| 最大値 | 0.577 | 1.000 | 1.000 |

最小値と幾何平均は同等で、最大値は使えない。**より単純で計算の軽い最小値を採る。**

### B.2 表示への写し方

確信度は 1 のごく近くに密集するため、線形に濃淡へ写しても差が見えない。対数軸で写す。

```
疑わしさ = clamp( (log10(1 - 確信度) + 4) / 3, 0, 1 )
```

0.9999 以上を 0（確か）、0.9 以下を 1（疑わしい）とする。この設定で、**誤った文字の 79% が
0.5 を超え、正しい文字の 86% は 0.5 未満**に収まった。

### B.3 実機での確認

雑音を強めた信号（送信 `CQ DE JA1ABC K TNX FER CALL`）を復号したところ、誤った文字は
すべて疑わしさ 1.00 に、正しい文字は 0.28〜0.58 に分かれた。

| 文字 | 確信度 | 疑わしさ | 判定 |
| --- | --- | --- | --- |
| C, Q, D, E（先頭） | 0.9945–0.9988 | 0.36–0.58 | 正しい |
| B → **D** と誤る | 0.4324 | **1.00** | 誤り |
| K → **C** と誤る | 0.5205 | **1.00** | 誤り |
| T → **C** と誤る | 0.7569 | **1.00** | 誤り |
| L, L（末尾） | 0.9993 | 0.28–0.29 | 正しい |

**誤った文字が確かな文字と同じ顔で出ることはなくなった**（要件 FR-C.2 の受入基準）。

## 付録 C — 遅延の見積りが誤っていた件

### C.1 何を間違えたか

版 2.0 で示した確定文字の遅延の内訳は、**推論間隔 + 推論時間 + 末尾ガード**の 3 項だけだった。
これは誤りである。**確定は語間でしか起こらない**という自分で書いた仕様（FR-B.3）を、
見積りに反映していなかった。

ある文字が確定するまでには、次の 4 つを待つ必要がある。

1. 推論の順番が回ってくるまで
2. 推論そのもの
3. **その文字より後に語間が現れるまで** ← 落としていた項
4. その語間が末尾ガードより手前に来るまで

語間は 20〜25 WPM でおよそ 2 秒に 1 回しか現れない。3 の待ち時間は平均で約 1 秒、
語が長ければ 2 秒を超える。**目標に据えた 3.0 秒は、はじめから届かない値だった。**

### C.2 実測

`cli/cw_stream` が、音声上の時刻と画面に出た時刻の差を測る。70 秒の QSO と、
雑音を強めた 15 秒の信号で測った結果が次のとおり。

| 音声 | 投入の刻み | 暫定文字の遅延 95% | 確定文字の遅延 95% | 確定部分の書き換え |
| --- | --- | --- | --- | --- |
| 70 秒 QSO | 0.5 秒 | **1.25 秒** | 4.48 秒 | 0 回 |
| 70 秒 QSO | 1.0 秒 | 1.92 秒 | 4.47 秒 | 0 回 |
| 70 秒 QSO | 2.0 秒 | 3.37 秒 | 5.42 秒 | 0 回 |
| 雑音つき 15 秒 | 0.5 秒 | **0.92 秒** | 4.09 秒 | 0 回 |

### C.3 どう直したか

**目標を実測に合わせて緩めた**（NFR-1.2 を 3.0 秒 → 5.0 秒）。設計を変えて 3 秒に収めることも
できるが、そのためには語間を待たずに文字単位で確定させることになり、**確定した文字が
後から書き換わる**危険を招く。体験目標 4「一度出た文字が勝手に書き換わらない」を
遅延のために手放すのは本末転倒である。

あわせて、**利用者が実際に読むのは暫定テキストのほう**だと位置づけを整理した。確定は
記録を落ち着かせるための背景処理であり、体験としての「待たされない」は NFR-1.1 が担う。
その 1.5 秒は実測 0.92〜1.25 秒で満たしている。

### C.4 投入の刻みが効く

暫定文字の遅延は、音声をどれだけ細かく投入するかにほぼ比例する（0.5 秒刻みで 1.25 秒、
2.0 秒刻みで 3.37 秒）。**GUI は録音を 0.2 秒ごとに取り込む**ため、実機ではこの表の
最良の行に近い。刻みを粗くすると目標を割るので、取り込みの間隔は広げないこと。

## 付録 D — 慎重な見直しで見つけた不具合

流し込み受信を入れた直後に、**それまでの実装との整合**を確かめる目的で全体を見直した。
機能を足す前に見つかった 4 件を記録する。いずれも動作するように見えていた。

### D.1 帯域制限を細切れに掛けていた（実害あり）

GUI は録音を 0.2 秒ごとに取り込み、**その断片ごとに**低域通過フィルタを掛けてから
流し込んでいた。FIR は前後のサンプルを必要とするため、断片の境目では過去の値が
無いものとして扱われ、そこに過渡が生じる。

合成信号で測ったところ、**継ぎ目の誤差は最大 0.55、信号そのものの実効値 0.31 を上回っていた。**
これが毎秒 5 回起きていた。

帯域制限を GUI からエンジン（`TStreamingDecoder`）へ移し、**解析の直前に、途切れのない
1 本の音声へまとめて掛ける**ようにした。あわせて、溜める音声を録音されたままの周波数で
保持するよう改めた（周波数変換の前に帯域を絞らなければ意味がないため）。

効果は測定できる。強い雑音の信号で、帯域制限ありは完全一致、なしは `FER` を `FIR` と誤った。

### D.2 解析の先頭に偽の文字が出て、そのまま確定していた

確定点は語間の中央に取るため、次の解析は必ず無音から始まる。その境目をモデルが短点と
読むことがあり、**細かく投入するほど、訂正される前に確定してしまう**。投入の刻みを
0.2 秒にしたときに `JH2XYZ JH2XYZ` の後へ `E` が 1 文字混入した。

窓分割の復号は同じ問題を端の除去（`DEEPCW_EDGE_GUARD_SECONDS`）で解決済みだった。
**同じ考え方を流し込みにも入れ**、解析開始から 0.08 秒以内の文字を捨てるようにした。
40 WPM でも語間の半分は 105 ms あるため、本物の文字を巻き込むことはない。

修正後は投入の刻み 0.1〜2.0 秒の 6 通りすべてで、一括復号と 1 文字も違わない。

### D.3 設定が保存されていなかった

「設定の永続化」は当初から実装済みとしていたが、**書き出しは終了処理からしか呼ばれて
おらず、実際に保存されたことを一度も確かめていなかった。**強制終了はもちろん、
検証時に窓を閉じても保存されなかった。

変更から数秒おいて書き出す方式に改め、**強制終了しても直前の設定が残る**ことを確認した。
あわせて、保存の失敗を握りつぶしていたのをやめ、診断情報に残すようにした。
設定ファイルの場所も診断画面に出す。

> **反省**: 実装済みと記した項目のうち、動かして確かめていなかったものがこれだった。
> コードがあることと、動くことは別である。

### D.4 使われない操作部が残っていた

流し込み受信に切り替えた際、受信タブの「窓 (秒)」「間隔 (秒)」は**値を保存するだけで
復号に一切影響しない**状態になっていた。利用者が動かしても何も起きない。

FR-B.3 の「速さ優先／確実さ優先」に置き換え、末尾ガードと最小確定長へ実際に反映するようにした。
あわせて、使われなくなった定数・変数・関数（`MergeOverlappingText` ほか）を削除し、
二重に定義されていた遮断周波数を一本化した。
