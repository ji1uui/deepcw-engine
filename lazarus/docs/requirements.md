## 2. 現状の把握

### 2.1 エンジンが提供するもの（実測値）

`model.onnx` / `model.onnx.json` を実測して確認した仕様。

| 項目 | 値 |
| --- | --- |
| サンプリング周波数 | 3,200 Hz |
| FFT 長 / ホップ長 | 256 / 48（ホップ 15 ms、66.7 フレーム/秒） |
| 周波数ビン | 400–1200 Hz を 65 ビン（分解能 12.5 Hz） |
| 正規化 | `log1p`（反射パディングあり、中心化フレーミング） |
| 文字集合 | 41 文字（A–Z、0–9、`,` `.` `/` `?`、空白）＋ブランク＝42 クラス |
| 入力 / 出力 | `[1,1,T,65]` / `[1,T,42]`、**時間方向のストライドなし（T は同一）** |
| 出力の意味 | **log-softmax**（各フレームの `exp` 総和が 1.000） |
| 音声長の制約 | 5–20 秒 |

**この 2 点は要件設計上とくに重要である。**

1. **確信度は追加コストなしで得られる。** 出力が log-softmax である以上、各フレームの最大値を `exp` すれば
   そのフレームの事後確率そのものになる。本レポート提案 3（確信度の可視化）は、モデルを変更せず、
   推論を追加せずに実装できる。
2. **文字の時刻は 15 ms 分解能で得られる。** 出力フレームと入力フレームが 1:1 であるため、CTC 経路上で
   文字を出力したフレーム番号がそのまま時刻になる。ウォーターフォールとの時間整合、語単位の再デコード、
   フィスト計測のすべてがこの一点に依存する。

### 2.2 リファレンス実装の機能棚卸し

web-deep-cw-decoder（v0.5.4）を読み、GUI アプリが参照すべき設計を抽出した。

| 領域 | リファレンス実装の設計 | 出典 |
| --- | --- | --- |
| 前処理 | 9,600 Hz / FFT 768 / ホップ 192、**パディングなし**、**per-sample CMVN 正規化** | `src/const.ts`, `src/utils/spectrogramUtils.ts` |
| 同調 | バンドパスではなく**周波数シフト**。目的ビンをモデル中心（800 Hz）へ移送し、残りは 0 埋め | `audioToShiftedSpectrogramTensor` |
| モデル構成 | `en`（標準 65 ビン）、`en_narrow`（5 ビン・パイルアップ用）、`ja`（**和文 67 文字**）、`detect_cw`（ビンごとの SNR 推定） | `src/utils/inferenceProtocol.ts` |
| 実行基盤 | Web Worker 上で ONNX Runtime、WASM / WebGPU 切替、WebGPU は逐次化 | `src/workers/inferenceWorker.ts` |
| ストリーミング | 語間で確定点を決め、確定テキストと暫定テキストを分離。最大 30 秒、末尾 1.25 秒は確定させない、推論間隔 1 秒以上 | `src/hooks/useStreamingDecode.ts` |
| 再デコード | 確定済み音声を 120 秒保持し、**単語をクリックするとその区間だけ再推論して候補を提示** | `src/StreamingTranscriptDisplay.tsx` |
| パイルアップ | `detect_cw` で最大 5 波を検出・追尾（ロック/リリース閾値 −10 dB）、各波を狭帯域モデルで並行デコード | `src/hooks/usePileupDetection.ts`, `usePileupDecode.ts` |
| 表示 | Canvas ウォーターフォール。**クリックで復調帯域を移動、ホイールで微調整**、輝度調整、DPR 対応 | `src/hooks/useCanvasInteraction.ts`, `useSpectrogramRenderer.ts` |
| 音声パススルー | 4 段バイキャッドの帯域通過を通して任意の出力デバイスへ。ニューラル雑音低減は別プロジェクト（HamNoise） | `src/hooks/useFilteredPassthroughStream.ts` |
| 設定 | 全設定を永続化。モード（Normal / Pileup / Benchmark）、復調窓 6/12/18/30 秒、帯域 100/150/250/500/800 Hz | `src/hooks/usePersistedState.ts`, `src/Decoder.tsx` |
| 自己計測 | ベンチマークモードで実時間比（xN）を表示 | `src/BenchmarkPanel.tsx` |

> **和文モデルは存在するが、本リポジトリには同梱されていない。**
> リファレンス実装は `models/ja/...` を実行時に取得する。`deepcw-engine` が配布するのは英文モデル 1 個だけである。
> 本レポート最多要望である和文対応は、**アプリ側の実装ではなくモデルの入手可否が律速**となる（3.2 参照）。

### 2.3 Lazarus 実装の現在地

| 実装済み | 未実装 |
| --- | --- |
| WAV ファイルのデコード（20 秒超は自動分割・結合） | 和文 |
| PortAudio によるライブ受信（窓スライド＋重複結合） | 確信度の可視化（値は取得できるが捨てている） |
| 送信（PARIS / ファンズワース、WAV 保存、再生） | 周波数シフト同調・ウォーターフォール上での同調操作 |
| CTC 貪欲デコードと**文字ごとの時刻**（`TDecodedChar.Seconds`） | パイルアップ |

## 3. 前提と制約

### 3.1 メタデータ仕様の拡張が必要（前提条件）

現行の `model.onnx.json` は `normalization` に `log1p` しか許さず、フレーミング方法（パディングの有無、
中心化するか）を表現できない。リファレンス実装の新世代モデルは **CMVN 正規化・パディングなし**であり、
現行スキーマでは記述できない。

**要求**: メタデータに以下を追加し、アプリは値に従って前処理を切り替えられること。

| キー | 値 | 既定（後方互換） |
| --- | --- | --- |
| `normalization` | `log1p` \| `cmvn` | `log1p` |
| `framing.pad` | `reflect` \| `none` | `reflect` |
| `framing.center` | `true` \| `false` | `true` |
| `input_seconds` | `{ "min": 5, "max": 20 }` | 現行のハードコード値 |

拡張しない限り、和文モデルや狭帯域モデルを同一アプリで扱えない。**これは FR-5・FR-6 の前提条件である。**

### 3.2 和文モデルの入手（未解決）

和文対応の可否は次のいずれかに依存する。アプリ側だけでは解決できない。

1. `deepcw-engine` が和文モデルを同梱・配布する（最も望ましい）
2. アプリが実行時に外部から和文モデルを取得する（配布ライセンスと通信要件の検討が必要）
3. 和文のみ従来型（ルールベース）デコーダで代替する（精度は本エンジンの水準に達しない）

**本書は 1 または 2 を前提に FR-5 を記述し、実現しない場合の縮退動作も定める。**

### 3.3 ライセンス

本リポジトリは **AGPL-3.0-only**。GUI アプリも同ライセンスで配布される。したがって:

- 本アプリを改変して第三者に提供する場合、ソースコードの提供義務が生じる
- ネットワーク越しにサービスとして提供する場合も同様の義務が生じる
- **プロプライエタリなログソフトと同一バイナリに静的リンクする実装は避け、プロセス間連携（ファイル・
  クリップボード・ソケット）で疎結合に保つこと**（FR-9 の設計制約）

### 3.4 外部ライブラリ

| ライブラリ | 必須 | 欠如時の縮退 |
| --- | --- | --- |
| ONNX Runtime | 受信機能に必須 | 送信・練習・WAV 保存は動作。設定画面に導入手順を表示 |
| PortAudio | ライブ入出力に必須 | WAV の読み書きのみで動作 |

### 3.5 デコーダの位置づけ（設計思想）

本レポートが繰り返し指摘するとおり、国内コミュニティはデコーダを**人間の耳と脳の置き換えではなく、
補助・練習の道具**とみなしている。本アプリはこの立場を設計に反映する。

- 誤りうる出力を、正しい出力と同じ見た目で提示しない（FR-4）
- 「読めない符号」を失敗としてではなく、送信者の個性として記録・可視化する（FR-8）
- 練習から実運用までを 1 つのアプリで完結させ、学習を能動的に支える（FR-7）

## 4. 機能要件

優先度は **必須**（初版に不可欠）／**推奨**（初版で強く望まれる）／**任意**（将来版で可）の 3 段階。
「根拠」は本レポートの該当箇所、またはリファレンス実装の該当ファイルを示す。

### FR-1 デコード中核 (Core decoding)

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-1.1 | メタデータに記述された前処理（サンプリング周波数、STFT 形状、帯域、正規化、フレーミング）に従い、モデル入力テンソルを生成する | 必須 | 3.1 の 4 キーすべてについて、値を変えると前処理が切り替わることをテストで示す |
| FR-1.2 | CTC 貪欲デコードにより、文字列と**文字ごとの開始・終了フレーム**を返す | 必須 | 既実装。時刻分解能 15 ms を維持 |
| FR-1.3 | モデルの入力長制限を超える音声を、重なりを持つ窓に分割し、端の誤りを時刻で除去して結合する | 必須 | 既実装。70 秒の QSO を 1 文字の誤りなく復号 |
| FR-1.4 | 復号は符号の 1:3 比を前提とする閾値処理を用いず、モデルの推論のみに依存する | 必須 | バグキー・縦振りの録音で、従来型デコーダより CER が悪化しないこと |
| FR-1.5 | 出力テキストを Python 参照実装と一致させる（同一モデル・同一入力） | 必須 | 既実装。回帰テストとして CI 化 |

> **FR-1.4 の意義**: 本レポート第一部 4 は「1:3 タイミングを前提とするすべてのデコーダで読み取れない」ことを
> 中核的欠陥として挙げる。DeepCW はタイミング比の仮定を持たないため、**この要求に対して構造的に有利**である。
> ただし優位性は測定して示す必要があり、FR-8 の記録機能がその材料を供給する。

### FR-2 同調と帯域制御 (Tuning)

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-2.1 | ウォーターフォール上のクリックで復調中心周波数を移動できる | 必須 | クリック位置と設定周波数の誤差が 1 ビン以内 |
| FR-2.2 | ホイール（または上下キー）で中心周波数を微調整できる | 必須 | 1 操作 = 1 ビン（12.5 Hz）以下 |
| FR-2.3 | 帯域幅を 100 / 150 / 250 / 500 / 800 Hz から選べる | 推奨 | 各設定で隣接信号の混入が減ることを聴感と CER で確認 |
| FR-2.4 | 同調は**周波数シフト方式**（目的ビンをモデル中心へ移送）で実装する | 推奨 | 700 Hz と 1100 Hz の同一信号で CER が同等 |
| FR-2.5 | 現在の復調帯域をウォーターフォール上に矩形で重畳表示する | 必須 | 表示帯域と実際の処理帯域が一致 |

### FR-3 ストリーミング受信 (Streaming)

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-3.1 | 受信テキストを**確定部分と暫定部分に分けて表示**する。暫定部分は視覚的に区別する | 必須 | 暫定部分が書き換わっても確定部分は不変 |
| FR-3.2 | 確定点は語間（空白）で決定し、末尾の一定時間（既定 1.25 秒）は確定させない | 必須 | 語の途中で確定しないこと |
| FR-3.3 | 解析窓の上限（既定 30 秒）と最小推論間隔（既定 1 秒）を設ける | 必須 | CPU 使用率が上限内（NFR-1.3） |
| FR-3.4 | 現行の文字列重複結合方式を FR-3.1 の方式へ置き換える | 必須 | 語の重複・欠落が発生しないこと |
| FR-3.5 | 受信中の音声を一定時間（既定 120 秒）保持し、再デコードに供する | 推奨 | FR-4.3 が動作すること |
| FR-3.6 | 受信テキストをログ／テキストファイルへ追記保存できる | 推奨 | タイムスタンプ付きで欠落なく保存 |

### FR-4 確信度と検証 (Confidence)

本レポート提案 3 に対応する。**2.1 のとおり追加コストなしで実装できる。**

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-4.1 | 文字ごとの確信度を、その文字を出力したフレーム群の事後確率から算出する | 必須 | 定義（最小値／幾何平均のいずれか）を文書化し、実装と一致させる |
| FR-4.2 | 確信度を**濃淡または色**で表示する。低確信度の文字は明確に薄く表示する | 必須 | 雑音のみの入力で出力される文字がすべて低確信度側に入る |
| FR-4.3 | 語をクリックすると、その区間の音声だけを再推論して候補を提示する | 推奨 | 提示までの待ち時間が 1 秒以内（NFR-1.2） |
| FR-4.4 | 確信度の表示強度をユーザーが調整、または無効化できる | 推奨 | 設定が永続化される |
| FR-4.5 | 全体の平均確信度を受信画面に常時表示する | 任意 | — |

> **設計上の注意**: 確信度は「正しさ」の保証ではない。UI 上でも「確からしさ」と表現し、断定的な語を用いない。
> 本レポートが警告する「誤表示されたコールサインを正しいものとみなすリスク」への回答がこの要件である。

### FR-5 和文 CW (Japanese Morse)

本レポート最多要望。3.2 の前提が満たされることを条件とする。

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-5.1 | 和文モデル（カタカナ 67 文字＋ブランク）を、英文モデルと同じ枠組みで読み込める | 必須 | メタデータの差し替えのみで動作すること |
| FR-5.2 | 「欧文」「和文」「欧文＋和文」の 3 モードを選べる。欧文＋和文では両モデルを並行実行し、2 段で表示する | 必須 | 並行実行時も NFR-1.1 を満たす |
| FR-5.3 | 欧文と和文を色で区別して表示する | 推奨 | 色覚特性に配慮（NFR-5.4） |
| FR-5.4 | 和文モデルを入手できない場合、和文機能を無効化し、理由と入手方法を設定画面に表示する | 必須 | 英文機能に影響を与えないこと |
| FR-5.5 | 送信側も和文符号に対応する（カタカナ、長音、濁点・半濁点、括弧、区切点） | 推奨 | 送信→自己デコードで往復一致 |
| FR-5.6 | 「ホレ」「ラタ」等のプロサインによる欧文／和文の自動切替 | 任意 | 切替点の前後で取りこぼしがないこと |

### FR-6 パイルアップ・複数信号 (Pileup)

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-6.1 | 帯域内の CW 信号を検出し、最大 5 波まで追尾する | 任意 | 検出周波数の誤差が 1 ビン以内 |
| FR-6.2 | 各波を並行してデコードし、ウォーターフォール上に周波数位置とともに表示する | 任意 | 5 波同時で NFR-1.1 を満たす |
| FR-6.3 | ロック／リリースにヒステリシスを設け、表示のちらつきを防ぐ | 任意 | 弱い信号で追尾が点滅しないこと |

> 狭帯域モデル（`en_narrow`）と検出モデル（`detect_cw`）の入手が前提。3.2 と同じ制約が及ぶため優先度は任意とする。

### FR-7 送信と練習 (Transmit and training)

本レポート提案 6 に対応する。**練習・実運用・記録を 1 つのアプリで完結させる**ことが目的。

| ID | 要件 | 優先度 | 受入基準 |
| --- | --- | --- | --- |
| FR-7.1 | テキストから CW 音声を生成し、再生・WAV 保存できる（PARIS 準拠、ファンズワース対応） | 必須 | 既実装 |

## 5. 非機能要件

### NFR-1 性能 (Performance)

| ID | 要件 | 目標値 | 測定方法 |
| --- | --- | --- | --- |
| NFR-1.1 | 実時間比 | 単一信号・1 スレッドで **10 倍以上**（実測値は 40–60 倍） | FR-13.5 のベンチマーク |
| NFR-1.2 | 語の再デコード応答 | **1 秒以内** | 操作から表示までを計測 |
| NFR-1.3 | 連続受信時の CPU 使用率 | 4 コア機で **1 コア相当以下** | 10 分間の連続受信で計測 |
| NFR-1.4 | ウォーターフォール描画 | **30 fps 以上** | 描画間隔の実測 |
| NFR-1.5 | 起動から受信開始まで | **5 秒以内**（モデル読み込みを含む） | 実測 |

### NFR-2 デコード精度 (Accuracy)

| ID | 要件 | 目標値 |

## 8. 本書が本レポートに応答できていない点

誠実さのために明記する。

- **移動運用の統合 UI（提案 5）** は本アプリの範囲外とした（7 章 6 参照）。
- **セルフスポット投稿・コミュニティ統合（提案 7）** は外部サービスへの依存と NFR-6.2 の制約から、初版では扱わない。
- **アワード進捗の自動判定（提案 3 後半）** は第三者データに依存するため、FR-10.4 として任意に留めた。
- **バグキー対応（提案 4）** は、エンジンが構造的に有利であることを示せるにとどまる。
  「芸術的な符号」をどこまで読めるかは、実際の録音による評価を経なければ約束できない。
